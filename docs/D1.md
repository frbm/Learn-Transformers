## Results

**Tests:** 25 pass (D1 and D2), on CPU and on CUDA with flex.

**Everything below is a smoke run.** The base model is the 3 M-token A4 RoPE checkpoint (Tier 0, T = 512), not the Tier 1 model of C1, which has not been trained yet (~40 min). Each SFT run is 30 steps. The numbers show that the pipeline works and which way the effects go. They are not results.

**Task 1: the data** (C2's `data/verse.jsonl`; split by duplicate cluster, kept from C2):

| | examples | prompt tokens (mean / p95) | response tokens (mean / p50 / p95 / max) |
|---|---|---|---|
| train | 5 311 | 17 / 28 | 476 / 351 / 1 305 / 2 687 |
| val | 291 | 17 / 29 | 471 / 358 / 1 240 / 2 103 |

Dropped as too long, and rows after first-fit decreasing:

| T | dropped | rows (train) | utilisation |
|---|---|---|---|
| 512 | 35 % | 1 725 | 98.6 % |
| **1024** | **10 %** | 1 774 | 99.6 % |
| 2048 | 1.4 % | 1 199 | 99.9 % |

T = 1024 (Tier 1's context) is the default: it keeps 90 % of the poems. A model trained at T = 512 loses a third of them, and the longest third at that, which biases the corpus towards short lyrics.

**Proposition 3** (4 new tokens, V = 16 384, 100 FineWeb contexts × 128 positions): max KL(old ‖ new) = 1.2e-4 nats, mean 4.2e-5, bound log(1 + 4/V) = 2.4e-4. The largest probability of a new token is 3.0e-5 < 1/V = 6.1e-5.

**Task 2.3: throughput** (one epoch at T = 512, B = 8, Tier 0 model):

| layout | useful tokens/s | peak memory | useful fraction |
|---|---|---|---|
| padded | 121 k | 2.38 GiB | 49 % |
| packed, dense mask | 156 k | 1.37 GiB | 99 % |
| packed, flex | 156 k | 1.37 GiB | 99 %, attention work 61 % of T² |

Packing doubles the useful fraction but gives only 1.29× the throughput: padded rows hold shorter sequences, which are cheaper per row. Flex and the dense mask tie here, because attention is a small part of a Tier 0 step at T = 512. Flex saves 39 % of the attention work (Σ L_j² / T²), and that matters at Tier 1 and T = 1024.

**Task 3** (smoke runs, 30 steps, lr 3e-4, token weighting):

| | verse val loss | FineWeb bpb (forgetting) | val entropy (nats) |
|---|---|---|---|
| base | 6.797 | 2.114 | 6.97 |
| λ = 0 | 5.300 | 2.224 (+0.110) | 6.39 |
| λ = 0.3 | 5.356 | 2.149 (+0.035) | 6.48 |

Replay at λ = 0.3 removes two thirds of the forgetting for 0.056 nats of verse loss: two points of the Proposition 5 frontier, trained and not minimised.

**Task 4** (smoke, 8 headers per n, 200 new tokens): the pipeline runs end to end, from control accuracy for the SFT model and for the base model with a plain-text header, through memorisation, to the train–validation gap. After 30 steps the SFT model does not obey `<|lines|>` yet, so the numbers are not worth recording.

## Answers

**Token or sequence weighting?** Token weighting is the default: it is the MLE of Proposition 1 on the empirical measure, and the loss is comparable to pretraining bpb. With poems from 4 to 120 lines, it gives the long poems most of the gradient. Sequence weighting fits P(y|c)^{1/|y|}, which treats each poem as one example and favours short lyrics. Both are computed over the whole optimiser step: `loss_denominator` counts tokens or poems across all K micro-batches before any backward.

**Where on the λ frontier would I ship?** To be decided on the full runs. The smoke run says λ = 0.3 keeps most of the verse gain and removes most of the forgetting. If the SFT model is only used for verse (D3, D4 and F1 sample only verse), forgetting matters little, and λ = 0 or 0.1 is the better point.

**Interview (60 s): what can go wrong in an SFT pipeline that a loss curve will not show you?**
- A wrong loss mask: the model fits the prompts (Proposition 1).
- Packing without a block-diagonal mask: examples condition on unrelated neighbours.
- Per-micro-batch means: the examples are weighted wrongly.
- Random init of new token embeddings: the model emits them everywhere.
- Silently dropped long examples: 35 % here at T = 512.
- Validation contaminated by near-duplicates of training examples.
- Entropy collapse: the model memorises, which the loss shows only as a gap.
- Control tokens the model ignores: you have to measure requested against realised.
- Forgetting of the base distribution: measure it on pretraining data.

## Research-engineering tricks

- **One loop, a pluggable objective.** SFT, replay and LoRA run on C1's `Trainer`. The objective returns per-micro-batch loss closures, already divided by the step's denominator. Schedule, clipping, accumulation, timing, logging and checkpointing are written once.
- **A bug the unification exposed.** The fp32 QK-norm gains promote q and k to fp32 under autocast, while v stays bf16. SDPA's autocast hides this; flex attention raises. The old SFT forward cast q and k by hand, and that line was lost when four forward copies became one. The model now casts once, before any kernel.
- **Measure the drop rate before you choose T.** 35 % of the poems vanish at T = 512, and they are the longest ones.
- **Mean-embedding init for new tokens.** By Jensen, the KL to the old model is at most log(1 + k/V). Check it numerically in fp64 on the CPU: 1e-4 nats is below bf16 resolution.
- **First-fit decreasing packing.** 99 %+ utilisation in a few lines of Python. Position ids restart per example (exact with RoPE anyway, Proposition 4).
- **Test packing against separate forwards.** In float64, the packed forward must equal each example alone, position by position.
- **The denominator before the backward.** Count loss-bearing tokens (or poems) over all K micro-batches first, then sum the numerators. Per-micro-batch means weight examples wrongly when masks differ.
- **Deterministic replay.** round(λK) of the K micro-batches are pretraining batches, so the replay fraction is exact at every step. The realised λ is logged.
- **Forgetting is measured, not assumed.** Every evaluation records FineWeb bpb next to the verse loss: the frontier comes from the logs.
- **Entropy by relative position.** `response_rel_pos` maps each response token to [0, 1) in one vectorised pass. The plot compares poems of different lengths.
- **xlogy-safe entropy.** `-(p log p)` with `nan_to_num`: a zero-probability token gives 0, not NaN.
- **One checkpoint format.** `save_model` writes atomically and carries the special tokens. `load_model` ignores unknown config keys, so old checkpoints keep loading.
